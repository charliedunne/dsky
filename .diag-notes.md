# dsky — Pi segfault diagnosis notes

- Target: Raspberry Pi 3 (aarch64, Debian bullseye, glibc 2.31, libstdc++ 6.0.28)
- Cross toolchain on host (Arch x86_64): aarch64-linux-gnu-gcc 16.2.0
- Symptom: segfaults when run on the Pi

## Binary facts
- `sw/build-app-pi/dsky`: aarch64 PIE, unstripped but debug sections are **stubs**
  (`.debug_info` = 229 B, `.debug_line` = 201 B) → `addr2line` is useless; correlate via disassembly + `nm`.
- NEEDED: SDL2 / ttf / image / gfx + pthread / libstdc++ / m / gcc_s / c.
- RUNPATH points at a host path → needs `LD_LIBRARY_PATH` on the Pi (set to `~/run`).
- Max version requirements: `GLIBCXX_3.4.26` / `CXXABI_1.3.9`, both **<** bullseye's 3.4.29
  → no load-time symbol-version failure. The loader is not the problem.
- `main` vaddr = `0x7ee0`; global pointer slot to `&std::cout` at vaddr `0x9ff68`.

## Crash site (Pi gdb — ground truth)
```
Program received signal SIGSEGV, Segmentation fault.
0x0000005555558cb0 in main ()          # = main+3536
sp = 0x7ffffff4d0 (valid), lr = main+3356
```
Faulting instruction at vaddr `0x8cb0` (= main+3536):
```
ldr  x1, [x0]        # load &std::cout from global slot @0x9ff68 into x1 (vptr)
ldur x1, [x1, #-24]  # deref cout's vtable at offset -24  <-- FAULTS (vptr == nil)
```
This is the **first real use of `std::cout`** in `main`
(`LogInfo << "Initializing core...\n"`, first statement in `sw/src/main.cpp`).

## Register / memory dump proving std::cout was never constructed
- `x0 (obj) = 0x7ff7c3c150 = _ZSt4cout (std::cout)`
- `x1 (vptr) = (nil)`
- First words of `std::cout` are all zero → null-vtable deref.

Systematic check — **all three** standard stream objects are all-zero at the crash:
```
cout=0x7ff7c3c150  <_ZSt4cout>:  0x0000000000000000  0x0000000000000000
                        +16:     0x0000000000000000  0x0000000000000000
cin =0x7ff7c3be18  <_ZSt3cin>:   0x0000000000000000  0x0000000000000000
                        +16:     0x0000000000000000  0x0000000000000000
cerr=0x7ff7c3bf30  <_ZSt4cerr>:  0x0000000000000000  0x0000000000000000
                        +16:     0x0000000000000000  0x0000000000000000
```
→ This is a **systematic libstdc++ iostream static-initialization failure**, not a one-off.

## ldd (clean — all deps resolve, nothing missing)
All SDL2/ttf/image/gfx + pthread/libstdc++/m/gcc_s/c resolve under `LD_LIBRARY_PATH=$HOME/run`.
No missing library → rules out a load/runtime-library absence cause.

## Root-cause classification: ABI / toolchain mismatch
- Build: cross **GCC 16.2.0**, `-std=c++20` (`sw/CMakeLists.txt:50`).
- Target runtime libstdc++: **6.0.28 (GCC 10)** on bullseye.
- The iostream global objects (`cout`/`cin`/`cerr`) are imported from the runtime libstdc++
  but arrive **unconstructed** at first use in `main`. No environment change can make
  `std::cout` self-construct — this is a static-init / ABI incompatibility introduced by
  building with a much newer compiler (`-std=c++20`, GCC 16) against an older target libstdc++.
- QEMU (bullseye glibc 2.31 sysroot, no-ASLR) reproduces the **same logical instruction**
  and `si_addr = -24` matches `[vptr-24]` with vptr=0 → host repro is consistent with Pi.

## VERDICT
**ABI / toolchain mismatch → rebuild path (NOT a runtime/env fix).**

The crash is a libstdc++ iostream static-initialization failure caused by the toolchain/target
skew (cross GCC 16.2.0, `-std=c++20` vs target libstdc++ 6.0.28 / GCC 10). No runtime or
environment change can fix it — `std::cout` cannot self-construct.

Fix: rebuild the app against a **bullseye-matching toolchain (GCC ~10, `-std=c++17` or lower)**
so the iostream ABI and static-init layout match the target libstdc++.
Note: re-compiling with `-O0 -g` on the *same* GCC 16 toolchain will **not** fix this — it is an
ABI/init mismatch, not an optimization artifact.

## Target signature (what a "matching" toolchain must look like)
**GCC 10.2.1 / glibc 2.31 / libstdc++ 6.0.28 (GLIBCXX_3.4.29)** — Debian bullseye userland,
aarch64 Cortex-A53 (ARMv8.0: no PAC/BTI/GCS hardware), kernel 6.1.21-v8+.

### Runtime graphics stack on the Pi (for completeness)
- SDL2 **2.0.14** · libX11 **1.7.2** (2:1.7.2-1) · EGL **1.5** (libegl1 1.3.2-1, libegl-mesa0 20.3.5) · Mesa **20.3.5**-1+rpt5+rpi1
- `~/run` ships only the SDL libs + app: bundled `libSDL2-2.0.so.0` needs ≤ `GLIBC_2.29`, ttf/image/gfx ≤ `GLIBC_2.17` → all fine on 2.31.
  `libstdc++`/`libc` resolve from the **system** (6.0.28 / 2.31) — nothing shadowed in `~/run`.

## Conclusion of this step
- The deltas that actually matter: **compiler major (16 vs 10)** and, as its ABI surface,
  **libstdc++ headers/link-target (3.4.36-era vs 6.0.28 runtime)**. glibc is *not* a load-time
  blocker (max `GLIBC_2.17` required) but constrains the sysroot choice for the fix.
- Codegen-feature deltas (TLS, stack-clash, PAC/BTI/CET) are all **non-factors** — verified off/compatible.
- Therefore "matching toolchain" = cross **GCC 10.x with a bullseye sysroot (glibc ≤ 2.31)**,
  `-std=c++17` or lower, default codegen (no PAC/BTI). Any GCC 10.x works: its libstdc++ tops out
  at GLIBCXX_3.4.29 = exactly the runtime's max. binutils version is irrelevant to the runtime.

# RESOLUTION — matching toolchain built, wired in, verified (2026-10-23)

## Toolchain recipe (self-contained user prefix `~/bullseye-cross`, no sudo needed)
- **Source debs (Ubuntu jammy, cross packages):**
  - `gcc-10-aarch64-linux-gnu` / `g++-10-aarch64-linux-gnu` = **10.3.0-8ubuntu1cross1**
    → drivers land at `~/bullseye-cross/usr/bin/aarch64-linux-gnu-{gcc,g++}-10`,
      backends at `~/bullseye-cross/usr/lib/gcc-cross/aarch64-linux-gnu/10/`.
  - `binutils-aarch64-linux-gnu` = **2.38** (as, ld, objdump, nm, ar, ...).
- Extracted with `ar x <deb> && tar xf data.tar.*` into the prefix (no dpkg install → relocatable).
- **patchelf `$ORIGIN` rpath fix on all 28 cross binutils tools**: they reference the
  multiarch `lib{bfd,opcodes,zlib,...}` dirs with absolute `/usr/lib/aarch64-linux-gnu` paths;
  without the rpath they only run if that host dir happens to exist. After patchelf they are
  fully self-contained inside the prefix.
- **CRT objects + libstdc++ symlink sourced from the Pi** (bullseye `libc6-dev`):
  `setup-pi-sysroot.sh` grabs `crt*.o` / `Scrt*.o` into the sysroot multiarch dir and creates
  `libstdc++.so -> libstdc++.so.6`. Reproducible, no host contamination.
- Result: `aarch64-linux-gnu-gcc-10 --version` = **10.3.0 (Ubuntu 10.3.0-8ubuntu1)**;
  sysroot glibc = **Debian GLIBC 2.31-13+rpt2+rpi1+deb11u5**; sysroot libstdc++ max =
  **GLIBCXX_3.4.28** (bullseye libstdc++6 6.0.28).

## The mandatory `-L<sysroot multiarch>` (why bare `-lstdc++` would be wrong)
- jammy's cross gcc has its own `gcc-cross/10/libstdc++.so` in its built-in LIBRARY_PATH — a
  **dangling relative symlink** with `libstdc++.a` beside it, listed FIRST. A bare `-lstdc++`
  would therefore silently **statically link jammy's libstdc++** (~1.4 MB binary) instead of the
  Pi's shared one.
- Fix: command-line `-L${SYSROOT}/usr/lib/aarch64-linux-gnu` (searched before LIBRARY_PATH) plus
  the sysroot multiarch `libstdc++.so -> libstdc++.so.6` symlink → bullseye's shared runtime wins.
  This is the only flag the toolchain file adds (`CMAKE_<LANG>_FLAGS_INIT`).
- C++ headers come from the toolchain's own `c++/10` (jammy GCC 10), not the sysroot, even with
  `--sysroot`; both are GCC 10 / GLIBCXX ≤ 3.4.28 → ABI-compatible. `--sysroot` alone re-roots
  the glibc includes correctly — no `-I`/`-nostdinc++` surgery needed (all removed).

## pkg-config host-path leak (the last build blocker) — diagnosis + fix
- **Symptom:** SDL's CMake feature checks (CheckEGL etc.) and plain `pkg-config --cflags/--libs`
  emitted **host** `/usr/include`, `/usr/lib` paths even though `PKG_CONFIG_LIBDIR` was pinned to
  the sysroot. Root cause: the `.pc` files *inside the sysroot* contain absolute `/usr/...`
  prefix values (copied verbatim from the Pi), so pkg-config happily emitted them — they point at
  the **host** filesystem, not the sysroot.
- **Options considered:**
  - (a) pkgconf wrapper script — insufficient alone: dbus/freetype `.pc` files carry literal
    paths that a wrapper can't generically re-root.
  - (b) **sed-rewrite of the `.pc` files in the sysroot** — chosen.
  - (c) disable SDL features to avoid pkg-config — rejected, wayland is required.
- **Fix = Step 4b in `sw/3rdparty/setup-pi-sysroot.sh`** (idempotent, applied to the existing
  sysroot directly): for each `.pc`, strip any prior `$ROOTFS` prefix, then re-root
  `/usr/lib` → `$ROOTFS/usr/lib`, `/usr/include` → `$ROOTFS/usr/include`, and the var defs
  `^prefix=/usr`, `^exec_prefix=/usr`, `^original_prefix=/usr` (optional trailing slash) →
  `$ROOTFS/usr`. After this, every `-I`/`-L` pkg-config emits is an absolute sysroot path (not a
  "system" path), so CMake's FindPkgConfig forcing `PKG_CONFIG_ALLOW_SYSTEM_CFLAGS/LIBS=1` is
  harmless — there are no host paths left to leak.
- **Idempotency bug caught + fixed:** the first version stripped `$ROOTFS/` *with* the trailing
  slash, which also removed the `/` before `usr`, leaving relative `usr/...`; the re-apply rules
  (matching `/usr/...`) then missed it → corruption on the 2nd pass. Fix: strip `$ROOTFS`
  **without** the trailing slash so pristine `/usr/...` is restored first. Verified idempotent
  across 3 passes (0 double-prefix, 140 files consistently re-rooted, 0 leftover pristine).
- **Verified:** real host `pkg-config` runs (with build.sh's `PKG_CONFIG_LIBDIR`) for
  dbus-1 / wayland-client / libpulse / freetype2 / egl / glesv2 show **zero host `/usr/` leaks** —
  every `-I`/`-L` points into `pi-sysroot`.

## Operational notes learned
- **Log buffering:** stdout→file means block-buffered stdio; the log file stays empty while the app
  runs idle and only flushes on buffer-full or clean exit. To capture startup logs: send SIGINT
  (handler → clean `main` return → stdio flush). SIGTERM/SIGKILL would *not* flush (no handler for
  SIGTERM; signal death skips stdio flush).
- **ssh + backgrounding gotcha:** `ssh host 'cd dir && setsid ... > log 2>&1 < /dev/null &'` HANGS —
  `A && B &` backgrounds the *whole AND-list*, so a subshell holding ssh's stdout pipe stays alive
  until dsky exits. Use `;` instead of `&&` so the redirections attach to the backgrounded command
  itself: `ssh host 'cd ~/run; setsid env ... ./dsky > dsky.log 2>&1 < /dev/null & echo $!'`.
